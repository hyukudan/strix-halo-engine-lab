# Strix Halo Sparse / PLE Lookup Lab

This lab isolates the large sparse-row access pattern used by PLE-style lookup
tables.

The initial target geometry uses:

- 2560-value embedding rows;
- BF16-sized rows as an initial byte model: 5120 bytes per row;
- 16 row requests per token window, corresponding to two n-gram orders with
  eight heads each.

The lab does not assume that the production path will use mmap, pread or a row
cache. It measures them separately.

## Build

```bash
cmake -S lab/sparse_lookup -B build/sparse-lookup -G Ninja \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/sparse-lookup
```

## Prepare a materialized test table

Do not benchmark a sparse hole-only file. Materialize deterministic bytes first:

```bash
./build/sparse-lookup/strix-sparse-lookup prepare \
  --file /fast/ple-table.bin \
  --table-rows 16384 \
  --row-bytes 5120
```

## Benchmark modes

### Direct mmap

```bash
./build/sparse-lookup/strix-sparse-lookup bench \
  --file /fast/ple-table.bin \
  --mode mmap --pattern ple \
  --table-rows 16384 --row-bytes 5120 \
  --requests 16000 --window 16
```

### One pread per requested row

```bash
./build/sparse-lookup/strix-sparse-lookup bench \
  --file /fast/ple-table.bin \
  --mode pread --pattern ple \
  --table-rows 16384 --row-bytes 5120 \
  --requests 16000 --window 16
```

### Bounded LRU row cache

```bash
./build/sparse-lookup/strix-sparse-lookup bench \
  --file /fast/ple-table.bin \
  --mode pread-cache --pattern ple \
  --cache-rows 256 \
  --table-rows 16384 --row-bytes 5120 \
  --requests 16000 --window 16
```

### Per-window unique-row coalescing

```bash
./build/sparse-lookup/strix-sparse-lookup bench \
  --file /fast/ple-table.bin \
  --mode pread-coalesced --pattern ple \
  --table-rows 16384 --row-bytes 5120 \
  --requests 16000 --window 16
```

## Access patterns

- `ple`: 16 logical head partitions with deterministic random row selection.
- `random`: uniform table-wide random rows.
- `hotset`: 80% of requests target a bounded hot set.
- `runs`: each logical window accesses a contiguous row run.

The `ple` pattern is the primary synthetic control. The others reveal whether a
candidate only wins because locality is unrealistically favorable.

## Cold versus warm

Use `--drop-cache` before a benchmark run to request page-cache eviction with
`POSIX_FADV_DONTNEED`.

Cold and warm results MUST be reported separately. A cache-friendly result must
not be presented as storage-path performance.

## Output

The JSON result reports:

- requested bytes;
- actual bytes issued through pread paths;
- read syscall count;
- cache hits and misses;
- major and minor page-fault deltas;
- requested-byte throughput;
- deterministic checksum.

For mmap, physical storage bytes are not inferred from the mapping. Page-fault
and system telemetry must be used instead.

## Qualification progression

1. synthetic table on local NVMe;
2. exact row size and request geometry from the canonical checkpoint;
3. access traces generated by the real PLE hashing path;
4. benchmark under simultaneous GPU decode load;
5. CPU gather to registered/staging memory;
6. optional direct GPU-visible access.

The winning path is the one with the lowest complete lookup-to-consumer cost
under real memory pressure, not the one with the highest isolated file-read
bandwidth.
