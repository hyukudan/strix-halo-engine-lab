# 06 — Quantization and Numerical Rules

## Decision

Numerical behavior is part of the engine contract.

Quantization, kernel fusion, speculative verification and batching MUST be qualified against explicit references.

## Validation layers

The engine MUST distinguish three different claims:

1. **model fidelity** — the engine implements the intended model and operator semantics, checked against an independent trusted oracle or fixtures;
2. **within-plan execution equivalence** — serial/optimized, solo/shared, fresh/resumed and speculative/serial paths preserve the same declared numerical plan;
3. **alternative numerical modes** — a different quantization, accumulation, prefill decomposition or distributed reduction plan may be valid, but requires separate fidelity qualification.

Agreement between two optimized paths is not sufficient proof of model fidelity because both paths can preserve the same implementation error.

## Separate contracts

The engine MUST distinguish:

- weight-storage quantization;
- activation precision;
- accumulator precision;
- KV-cache precision;
- recurrent-state precision;
- sampling precision.

Changing one does not authorize changing the others.

## Numerical-plan identity

Every qualified execution plan SHOULD identify at least:

- weight interpretation and execution layout;
- activation and accumulator precision;
- reduction and contraction policy;
- sampling algorithm and deterministic tie rules;
- prefill arithmetic/chunk plan when relevant;
- distributed partition and reduction order when relevant.

Retained state, snapshots, graph plans and tuning records MUST be invalidated when an incompatible numerical-plan component changes.

## Packed execution

Packed weight formats SHOULD be consumed directly by kernels.

Temporary or cached dequantization MAY be used when bounded and demonstrably faster.

Full-model expansion to wider formats SHOULD be avoided on a unified-memory system because it sacrifices context and concurrency capacity.

## Accumulation

Reduction and accumulation precision MUST be declared per operator family.

FP32 accumulation SHOULD be the conservative default for numerically sensitive reductions unless a lower-precision path is qualified.

Compiler contraction, denormal handling and approximate transcendental operations MUST be controlled where they can change token decisions or recurrent state.

## Row invariance

Any multi-row decode or verify kernel MUST be tested against the same row executed alone.

Batching MUST NOT silently change the arithmetic of a request unless that difference is an explicitly qualified mode.

## Deterministic ties

Routing, top-k selection and any discrete choice with equal scores MUST have a deterministic tie rule.

The rule MUST be identical between:

- reference implementation;
- optimized kernel;
- batched execution;
- speculative verification.

Sampling randomness SHOULD be keyed to stable logical properties such as an explicit seed and absolute token position. It MUST NOT depend on a transient worker slot, rejected speculative work, transport epoch or the node that happens to execute the sampler.

## KV quantization

KV quantization MAY be supported as a separate capacity mode.

It MUST:

- have its own memory accounting;
- use explicit group/scale geometry;
- validate fresh and resumed prompts;
- validate serial and speculative decoding;
- expose that model output may differ from the higher-precision cache.

The engine MUST NOT present a quantized KV mode as numerically identical unless it has been proven so.

## Golden references

Reference outputs SHOULD be generated by a simple, transparent implementation.

A failed optimized kernel MUST NOT be "fixed" by updating golden outputs.

Tolerance changes require a documented numerical reason.
