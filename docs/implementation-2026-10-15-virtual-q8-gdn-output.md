# Virtual256 Q8 GDN output projection (experimental)

`--virtual-q8-gdn-output` selects a one-wave Q8_0 output projection while retaining the original256-leaf arithmetic. It is independent of input-projection variants. The decoder admits every executed GDN output tensor before device setup: unique original name/layer/role, local placement, exact Q8_0 type, dimensions and packed byte count. The current model has36 output matrices of6144 input features by2560 output rows. The launcher independently rejects a wrong format or unaligned input width before any operator enqueue; there is no per-launch format fallback under this identity.

Original leaf t accumulates features t,t+256,... from positive FP32 zero with the existing decoder expression and FP32 FMA boundaries. Candidate lane l owns eight independent leaves t=8*l+j. The chunk loop retains ascending features separately for each leaf. Shuffle distances16,8,4,2,1 at fixed j reproduce old reduction strides128,64,32,16,8; register strides4,2,1 finish the same tree with the same left/right operands. The final existing float_to_bf16 bit-rounding function is unchanged. No input quantization, global FP option or weight transformation is introduced.

Default kernel bodies, IDs, compiler IDs and launcher identities remain unchanged. The new mode has distinct kernel/compiler/launcher identities and validates selected output suffixes independently of existing input-mode suffixes. It remains an experimental variant; graph eligibility follows the original device-input contract and still requires separate qualification.

A focused test-only same-TU fixture captures both actual original256-thread and candidate32-thread projection nodes, checks distinct functions and geometry, and replays them in isolation. It verifies exact BF16 receipt equality, independent CPU256-leaf FMA/tree results for finite cases, aligned partial chunks, the actual6144 width, output overlaunch guards, different poisons/no-op controls and immutable input/weights. Constructed FMA and accumulator-zero witnesses differ after BF16 storage; negative underflow and finite extreme inputs are included. NaN/signaling-NaN/infinity cases compare raw BF16 receipts against the actual original device kernel without asserting portable CPU NaN-payload semantics. Wrong dtype/alignment rejects specifically and preserves output. This fixture includes the production translation unit only for tests and adds no public diagnostic entry point.

Status: prototype, strict CPU tests and host-side HIP syntax checked. Actual target compilation, linked fixture/app code-object identity, oldfunction/descriptor preservation, candidate dependent FMA/tree/decoder/BF16 ISA, native fixtures, full original554-array/512-ID fidelity and512-token alternating benchmark remain required. Source equality is not compiled-code equality. No speed or occupancy claim follows from the source or short mixed conditioning/decode profile.
