# Weight plans and image ownership

Home: shared (host shared selection and cache identity; backend core runtime callbacks).

A storage descriptor never chooses numerical arithmetic. Each request names its admitted tensor, arithmetic, backend and incumbent kernel. The resolver checks eligibility before cost and retains the incumbent when no measured decision matches the exact compiler, device and workload. FAST requires explicit permission and a named contract. An image budget failure does not change arithmetic. Operand-exact test permission cannot become a model execution route.

`STRIX_WEIGHT_MEASURED_DECISIONS=0` is the rollback declaration for qualified replacements; family environment readers pass its resolved value through the shared helper. Strategy overrides use the typed request and fail if no eligible qualified registration exists. Missing throughput calibration produces an unavailable cost, never a fabricated prediction. Initial decision tables contain no replacements.

Measured tables use `wfmt.decisions@2` and require a source commit, compiler identity and flags, device, exact shape regime, versioned arithmetic, byte-receipt digest, byte equality and a measured speed result. Rows also require `build_identity`, `incumbent` and `replacement` as 64-hex content digests. The caller must verify the running executable/kernel-module digest and each registered implementation against the loaded artifacts before setting `ResolveRequest::build_identity` and `Candidate::implementation`; copying identities from receipts is forbidden. Missing identities decline replacements. The resolver matches these identities before translating a persistent implementation to a unique build-local dispatch ID. Version 1 numeric-ID tables are rejected. Registration order breaks ties. Import validates bounded metadata and rejects duplicate or unknown semantic keys. Receipts remain qualification inputs; importing metadata does not establish a device or full-model gate.

The cache reserves image and conversion workspace before work begins. Concurrent identical acquisitions share one conversion. Consumers wait for publication readiness; independent readers do not wait for each other's last-use events. Eviction requires all leases released and all recorded use complete. Content keys include source and sidecar digests, parameter metadata, tensor, slice, strides, shape, format, image, arithmetic, backend, architecture and ABI. A cache belongs to one backend/device. Failed last-use streams survive into retirement; the backend must fence/drain them or quarantine the allocation. Reservations remain charged through deferred reclamation, and workspace through readiness. Runtime callbacks may run under cache locks, must not re-enter the cache, and retirement must not throw. Their blocking latency needs qualification before concurrent serving adoption.

CPU allocation, copy and completion are immediate. Native runtime adapters provide vendor-local primitives with shared retirement mechanics. The native retirement service polls completion even when idle. After all contexts/caches stop submitting work, `shutdown_native_runtime()` joins the worker and drains pending events/streams; failed drains quarantine allocations and their charges. Shutdown is terminal for that backend runtime. Default-stream pageable uploads are explicitly completed before publishing readiness on a consumer stream. This serial staging path has no loading-performance qualification. Uncompiled adapters refuse explicitly. Intel's existing opaque queue has no event publication interface; an event-capable adapter must be supplied before cached images can be used there. No implicit host offload is performed.

## Load-time matrix storage

A family can tag BF16 matrix roles in its tensor schema and declare a versioned `WeightLoadPolicy`. The load plan applies to the complete tagged set. Changing the set, transcode rule or numerical bundle requires a new policy revision. The backend supplies the intersection of storage formats supported by all routes admitted for those roles, including the head and any prefill route or fallback that can execute with the image.

`resolve_weight_load` takes the resolved profile tier. EXACT uses BF16. FAST and TURBO select the target when the backend declares support and the decision table holds a gate v2 PASS and a measured workload gain for the same policy revision, backend, device, compiler, build, checkpoint and workload regime. Both receipts apply to the complete tagged set. The build field is `implementation_identity` of the versioned arithmetic of every consumer route the policy admits (projections, head, prefill tile and fallbacks), not the executable digest: a table compiled into an executable cannot name the digest of that executable. A consumer whose accumulation order changes bumps its arithmetic revision, which retires the row. The checkpoint field is the raw SHA-256 of the checkpoint file. The caller verifies the identities of the running code and the loaded checkpoint. An explicit qualification-arm request can select a runnable plan before receipts exist, with status `unqualified`.

The loader sizes each compact image using `matrix_load_geometry`. `load_bf16_matrix` reads the little-endian checkpoint slice into the planned image. Q8_0 stores 34 bytes per 32 consecutive weights, with a binary16 scale and signed 8-bit codes. The loader uses the shared block encoder and bounded staging. It rejects nonfinite inputs and FP16 scale overflow. Block scales that fall below the FP32 normal range round to zero in FP16 and use an all-zero block. The caller publishes storage and selects the matching backend weight view only after the complete load succeeds.

The `strix-hip-decode-token` loader and the Qwen Flash-Next CUDA `Prefill` loader resolve native Q8_0 indexed-attention output projections (`blk.N.attn_output.weight`) after tensor admission. The family adapter supplies the incumbent for the active backend and HIP decode profile. The common resolver returns the native packed rows and the incumbent launch ID. HIP binds that ID in the serial indexed-attention launcher and checks the resolved extent against device-visible storage. CUDA uses the resolved file range for upload and binds the existing dense A8 projection to the loaded layer. Both execution receipts include `qsa_output_weight_plans` with each tensor's storage, image, arithmetic, kernel ID and packed bytes.

The migration covers native Q8_0 trunk weights on those routes. Other source formats, alternate weight images and HIP prompt/window launchers use their existing routes. The native plan API refuses a request for another format with a reason. It has no conversion candidate. Device compilation and comparison of token IDs and uploaded bytes are pending.

Canonical family configuration objects can attach `FamilyPlans` through `attach_weight_plans`. Configuration inspection that runs before plan resolution reports pending plans.

Host checks cover eligibility, exact decision regimes, malformed imports, concurrent publication, budget and event failures, sidecar invalidation, deferred retirement, and configuration attachment through the GLM fixture. The Qwen tensor-table fixture compares the native Q8_0 representation, layout, byte extent and launch ID to the previous HIP and CUDA selections. Existing numerical paths remain the device comparison baseline.
